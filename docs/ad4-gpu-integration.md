The optional adapter is implemented and locally accepted within the explicitly
limited Apple-Silicon scope. Vina remains the default. This does not establish
AD4 superiority, validate an arbitrary user target, repair the one-work-item
configuration, or certify Windows/Linux GPU builds.

## Common reporting, distinct method

The adapter feeds the existing collector, Meeko export, Butina clustering,
representative analysis, PLIP, local 2D renderer, PyMOL and PDF generators.
There is no parallel production “GPU benchmark report” implementation.
Historical benchmark PDFs are preserved with their point-in-time limitations.

Protocols lock the AD4 profile, pinned executable identity and actual AutoGrid
extents. The native output mapping retains the original XML run ordering,
including printed-energy ties. Actual AD4 estimated binding energy is distinct
from the GPU’s total search energy and from Vina energy. No Vina effort or output
window is reinterpreted as an AD4 parameter. CPU controls are disabled for GPU
search and do not overwrite the user's saved Vina CPU choice.

The GUI’s short engine explanation and detailed offline settings guide cover
the distinction between scoring, searching and hardware; AD4 energy terms;
non-comparable cross-engine energies; genetic runs, heuristic budget and
autostop; grid rounding; supported chemistry; platform boundaries and limits.
The [learning guide](ad4-gpu-guide.md) provides the same explanation in the
documentation, with optional primary-source links.

## Failures found and retained during integration

An initial scripted click used a stale GUI revision and was correctly rejected
before searching. The harness now waits for output registration and refreshes
the visible state. A second preflight exposed source-versus-installed command
dispatch; an explicit validation command path is now preserved by the host.
Neither rejected attempt launched docking.

The regression suite also exposed stale completion status between consecutive
screens. A newly tracked screening job now records “running” before launch;
previous results remain viewable, but cannot masquerade as completion of that
new run. The serialized slot waits for the preceding coordinator’s short output
registration cleanup, without overlapping scientific workers. Optimistic
revision checks remain enforced.

A report-only helper initially lacked its hash import; the failed record and
copied inputs remain retained. A test initially compared macOS `/var` and
`/private/var` aliases rather than resolved paths; its failed run is preserved.
Two first-attempt 2D layouts failed strict collision checks and required wider
supported spacing. Report-only corrections reuse the completed native results;
they do not repeat preparation or docking.

Verified materialized bundle inputs are now retained inside new screens rather
than depending on a temporary extraction surviving indefinitely. Raw JSON
protocols retain their existing source-relative interpretation; the application
does not copy an arbitrary parent directory.

## Installation and platform boundary

Local installation **passed**: 25 explicit production files and the pinned
executable were deployed with recoverable backups, not a whole-environment
reinstall. Its record verifies installed source hashes, the
pinned executable, normal (non-validation) runtime discovery, retained-result
skip behavior and unchanged Vina executable/original user study. Activation is
the last deployment step. See the installation result in the records below for
the actual local status; a source acceptance record alone does not claim an
installation on another computer. All 59 native PyMOL checks also pass against
the installed modules. A normal installed GUI smoke check confirms that Vina
opens as the default, the AD4 option is available, its own fields replace Vina
fields, and the offline teaching guide opens. Restart the desktop application
to load the installed version; choose the optional engine in **Finalize
protocol → Docking program** when creating an explicitly AD4 exploratory recipe.

Shared settings, protocols, reports and GUI paths are intended for macOS,
Windows and Linux. Only the tested Apple-Silicon OpenCL build is accepted here.
Production AD4 control calibration, macrocycles/special atom types, flexible
receptors and Windows/Linux GPU build/driver acceptance remain outside this
release. The one-work-item defect is contained by a guard, not repaired.
